# Select native autonomous execution through autoApprove

Implementation and qualification progress is tracked in
[the stage-three evidence (historical private reference)](../testing/private-history.md).
The requirements below remain the completion gate; implementation commits do
not by themselves establish real-Harness qualification.

For the planned V0.1.12 migration, `autoApprove` selects an Adapter's declared native autonomous execution mode and approves any remaining native Approval Requests once. Kimi maps to native `auto`, Codex maps to its approval-and-sandbox bypass behavior, and OpenCode targets native `--auto` semantics, including preservation of explicit deny rules; the corresponding server integration still requires qualification. This accepts Harness-specific permission and interaction changes to serve autonomous consumers such as grilling, while preserving the existing meanings of `interactive`, `autoDeny`, and `harnessManaged`; it intentionally supersedes the prior requirement to implement `autoApprove` solely through request replies in ADR-0025, ADR-0089, and ADR-0118 where applicable, and revises the expectation of approval-event occurrence while retaining ADR-0078's pairing for actual requests. It does not claim equivalent authority or successful execution across Harnesses.

There is no separate public YOLO switch or selectable legacy request-by-request automatic approval strategy. The public Capability Profile shape stays unchanged: `approvalPolicies` declares supported policies, while `turnQuestions` describes Question lifecycle support without promising Questions in every mode. Native mechanisms and authority differences belong in Harness documentation and qualification, not new public mechanism or authority fields. Actual remaining requests use the existing `allowOnce` reply and requested/resolved event contract, with successful policy resolutions marked `source: policy`; reply failures must not be reported as successful approvals. Muha never fabricates requests or resolutions for actions the Harness executes without asking. A native denial without a request is not an approval opportunity. The SDK preserves the independent Question lifecycle and ADR-0096's absence of an implicit timeout; grilling instead initiates Turn interruption immediately on an unhandled Question and reports `UNEXPECTED_INTERACTION` after interruption cleanup, without waiting for a naturally completed Turn or adding automatic answers, dismissal, or a new Question policy.

Native Sessions may persist the selected mode; closing a Muha handle does not promise restoration of the previous mode, including after abnormal exit, and direct native resumption may inherit it. Muha must not implement Session policies by modifying persistent user or Workspace permission configuration. Every Muha creation or resumption must establish the currently selected policy, including when returning to `interactive` or `autoDeny`, and report application failure rather than execute under an inherited mode. This records accepted requirements, not a completed implementation: concrete protocol mappings, actual persistence, policy-dependent Questions, and OpenCode's Session-tree coverage and isolation still require qualification. OpenCode Session-wide all-allow rules are no longer the selected target. Its v1.18.25 `run --auto` implementation replies `once` to requests in the active Session tree on the client side, so Muha can implement those approval semantics through its existing server protocol and reply path without adding an unsupported `serve --auto` flag. This explicit native-equivalent mapping does not imply adopting unrelated `run` defaults for Questions or planning tools.
