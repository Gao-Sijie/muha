# Bind MCP and Skills to the Workspace

MCP servers and Skill sources belong to a Workspace rather than an Agent Session, while Approval Policy remains entirely separate from the Workspace. Through explicit `configureWorkspace`, Muha may write caller-supplied Skills and MCP settings into the target Harnesses' native project configuration but does not define a common MCP manifest. The targets default to every Harness enabled in that Muha Runtime; callers may instead select a non-empty subset, but cannot configure a Harness the Runtime has not enabled. Caller-supplied entries replace conflicting same-name Skill or MCP entries while unrelated native configuration is preserved. Path validation and permitted directory creation determine whether configuration returns a normalized `workspacePath`; Skill and MCP operations then run best-effort, isolating failures, continuing independent operations, retaining successful writes without rollback, and returning all structured per-Harness configuration results alongside that path. The same path may be configured repeatedly, with each call applying only its current inputs; Runtime serializes only its own concurrent configuration calls for the same normalized path to avoid self-inflicted read-modify-write races. Configuration may run while Sessions or Turns use the path, but its results attest only to filesystem writes: Muha does not pause or restart them, promise hot reload, or expose a common reload operation. After any call, native files are externally mutable and authoritative: Muha does not watch, restore, overwrite, validate, prevent concurrent external modification, or otherwise govern later changes made by a Harness or user. Session resumption therefore accepts no Skills or MCP input and uses the Workspace's current contents as-is.
